### 1.1 Shattered Pixel Dungeon — 열린 소스 픽셀 로그라이크의 창 시스템 [1차]
저장소: https://github.com/00-Evan/shattered-pixel-dungeon (GPL-3.0) — `core/.../Chrome.java`, `ui/Window.java`, `windows/Wnd*.java`, `scenes/PixelScene.java`를 직접 읽었다.

**도트 단위 · 배율**
- 화면 전체를 **정수 배율 하나(zoom)**로 키운다. 가로 모드 최소 가상 화면 = **240×160 도트** (`MIN_WIDTH_L/MIN_HEIGHT_L`). zoom = min(가로/240, 세로/160)의 내림, 기본값은 `ceil(density × 2.5)`를 그 안에 가둔다.
- 우리 기준 기기(915×412 CSS, DPR 2.625 = 2402×1082 기기 픽셀)에 넣으면: 최대 zoom = min(10, 6.76) → **6 기기 픽셀 = 1도트 ≈ 2.29 CSS px**. 가상 화면 ≈ **400×180 도트**. → 우리 `--px: 2px`(장치 층 1도트)와 거의 같은 밀도다. 아래 숫자를 그대로 옮겨 써도 된다.
- **배율은 기기 픽셀 기준 정수**다. CSS px 기준이 아니다. (→ 3.5절 「DPR 2.625 함정」)

**창 틀 (9-slice, `Chrome.get`)** — 원본 시트 `interfaces/chrome.png` 128×64
| 부품 | 원본 크기 | 테(slice) | 우리 화면 환산(×2.29) |
|---|---|---|---|
| WINDOW (기본 창) | 20×20 | 6 | 테 ≈ 14 CSS px |
| WINDOW_SILVER | 22×22 | 7 | ≈ 16 |
| TOAST | 9×9 | 4 | ≈ 9 |
| RED_BUTTON / GREY_BUTTON | 6×6 | 2 | ≈ 5 |
| SCROLL (이야기 창 · 종이) | 32×32 | 좌우 5 · 위아래 11 | — |
| TAB_SELECTED | 8×13 | 3·7·3·5 (비대칭) | — |
- 교훈: **창 테는 원본 20도트 중 6도트(30%)**, 단추 테는 6도트 중 2도트. 테 두께는 부품 위계를 따른다: 창 > 토스트 > 단추. 이야기(서사) 창은 **다른 재질(두루마리)**로 시스템 창과 구별한다.

**창 크기 · 여백 (상수 그대로)**
| 창 | 폭(가로 모드) | 우리 화면 비율 | 비고 |
|---|---|---|---|
| WndOptions (확인 · 선택지) | 144도트 | **36%** (≈330 CSS px) | 세로 모드 120 |
| WndTitledMessage · WndInfoItem (정보) | 120 → 글이 100도트 넘게 길면 20씩 넓혀 **최대 220** | 30% → 55% | 높이 상한 = 화면 높이 − 10도트 (≈ 94%) |
| WndStory (이야기) | 180 | 45% | 두루마리 틀, 아무 데나 누르면 닫힘 |
| WndChooseAbility (하나 고르기) | 130 | 33% | 선택지 오른쪽에 20도트 「i」 정보 단추 |
| WndGame (메뉴) | 120 | 30% | 단추 높이 20 |
- 여백 `MARGIN/GAP = 2도트`(≈4.6 CSS px), 제목 아래 `2×MARGIN`, 선택지 묶음 앞 `3×GAP`.
- **단추 높이 18도트**(≈41 CSS px), 단추는 **창 폭 전체 · 세로로 쌓는다**. 정보가 붙은 선택지는 `폭−18`짜리 단추 + 오른쪽 18×18 정보 단추.
- 글: 제목 9도트(≈21 CSS px), 본문 6도트(≈14 CSS px). 제목은 아이콘 + 이름(`IconTitle`, 사이 2도트), 제목 색은 노랑 `0xFFFF44` 한 가지.
- **창 바깥을 누르면 닫힌다**(`Window` 생성자의 `blocker` → `onBackPressed`). 뒤 화면은 `ShadowBox` 50%로 눌러 놓고 **맥락은 보인다**.
- 창 위치는 **안전 영역(safe insets) 안에서 가운데**. 노치 쪽 여백을 먼저 빼고 가운데를 잡는다.
- 정보 창이 길어지면 **세로로 늘리기 전에 가로로 넓힌다**(가로 모드에서 화면 밖으로 넘치지 않게 — 소스 주석 「window can go out of the screen on landscape, so widen it」).

### 1.2 Apple Human Interface Guidelines — Alerts · Modality · Buttons · Layout [1차]
https://developer.apple.com/design/human-interface-guidelines/alerts · /modality · /buttons · /layout
- 경고창은 **제목 + (있으면) 짧은 본문 + 단추 최대 3개**. 제목은 **두 줄을 넘기지 않는다**. 본문은 「가치가 있을 때만」. **스크롤되는 경고창은 피한다.**
- **정보만 주는 경고창은 쓰지 않는다** — 행동이 없는 정보는 맥락 안(표시 · 토스트)에서 준다. 흔하고 되돌릴 수 있는 행동에는 확인창을 띄우지 않는다. **되돌릴 수 없는 드문 행동에만** 확인창.
- 단추 이름은 **결과를 말하는 동사 1~2단어**(「확인/예/아니요」 대신 「지운다」). 취소는 늘 「취소」.
- **기본(가장 그럴 법한) 단추는 줄의 끝쪽(오른쪽)**, 취소는 앞쪽(왼쪽). 세로로 쌓으면 기본이 위.
- 의도하지 않은 파괴 행동만 파괴 색. 파괴 행동이 있으면 반드시 안전한 취소가 있다.
- 눈에 띄는 단추는 **한 화면에 1~2개**. 여러 선택지는 **크기가 아니라 스타일로** 구별한다(같은 크기 = 같은 묶음).
- 단추 누름 면적 **최소 44×44 pt**, 누름 상태를 반드시 둔다.
- 모달은 짧고 단순하게, **모달 안에 또 계층을 만들지 않는다**(「앱 속의 앱」 금지), 닫는 길은 늘 분명하게.
- 레이아웃: 중요한 것은 위 · 앞쪽(왼쪽 위), 정렬로 관계를, 들여쓰기로 종속을, **점진적 공개**로 처음 보이는 양을 줄인다. 가로 고정 게임도 안전 영역 · 여백을 지킨다.

### 1.4 Godot 엔진 문서 — 정수 배율 · 9-slice [1차]
https://github.com/godotengine/godot-docs `tutorials/rendering/multiple_resolutions.rst`, `classes/class_ninepatchrect.rst`
- 「Stretch Scale Mode = integer」: 배율을 **정수로 내림**(2.5 → 2.0), 남는 자리는 검은 띠. 분수 배율은 「체크무늬가 고르지 않고 선 두께가 들쭉날쭉」해진다 — 문서 그림으로 비교.
- NinePatchRect: 모서리는 그대로, 변은 한 축으로, 가운데는 두 축으로. 늘이기(STRETCH)는 **찌그러질 수 있다**, 반복(TILE)은 **찌그러지지 않지만 무늬가 이음매 없이 이어져야** 한다. → 무늬 있는 변은 반복, 단색 변만 늘이기.

### 1.5 Into the Breach (Subset Games) [2차]
- Justin Ma: 「**명확함을 위해서라면 멋진 아이디어를 매번 버린다.** 명확하게 보여 줄 수 있으면 넣는다.」 — gamedeveloper.com 인터뷰 (https://www.gamedeveloper.com/design/-i-into-the-breach-i-dev-on-ui-design-sacrifice-cool-ideas-for-the-sake-of-clarity-every-time-)
- UI가 버틸 수 있게 **설계 자체를 제한**(한 행동이 거는 상태 수 제한, 공격 유형 · 방향 제한). 무기 설명은 **움직이는 미리보기 툴팁**. GDC 2019 「Into the Breach Design Postmortem」(Matthew Davis) https://www.gdcvault.com/play/1026333
- 턴 종료에 확인창이 없다 — 대신 **적 의도가 판 위에 늘 보이고**, 되돌리기(이동 취소)와 판 되감기(횟수 제한)가 **늘 같은 자리**에 있다. 확인창 대신 예고 + 되돌리기.

### 1.9 Inscryption · Hades · Dead Cells · Monster Train · Wildfrost · Cogmind [2차]
- Inscryption: 저울 · 촛불 · 종 같은 **탁자 위 물건이 곧 UI**(디제틱). 다만 「메뉴 탐색이 번거롭다」는 평 — 물건 UI도 **누를 수 있는 것은 단추처럼 보여야** 한다.
- Hades: 은혜 선택 화면에서 「교체인지 강화인지」가 안 보여 혼란(Steam 토론) → 선택지에는 **결과(무엇이 바뀌나)를 한 줄로** 붙인다.
- Dead Cells(Motion Twin): 「어떤 거리에서도 UI가 읽히게 하는 것이 가장 어려웠다」(MCV 「When We Made Dead Cells」).
- Monster Train: 턴 결과를 **미리 계산해 확정 전에 보여 준다**(https://blog.lauramichet.com/monster-train-2/).
- Wildfrost 사운드: 「클릭은 클릭처럼, 호버는 호버처럼」 — 피드백은 기능과 맞는 소리.
- Cogmind(Kyzrati): 숙련자가 **다른 창을 열지 않고** 필요한 정보를 보게 기본 화면을 설계, 45줄 화면에 맞추려 창을 줄이면 「비좁다」 — 정보량과 비좁음의 균형(https://www.moddb.com/games/cogmind/news/full-ui-upscaling-part-2-holy-mockups).

### 1.10 게임 UX 이론 [2차]
- **Celia Hodent, *The Gamer's Brain***: 게임 UX = **사용성(usability) + 몰입성(engage-ability)** 두 기둥. 사용성 기둥은 Nielsen 휴리스틱(1994)을 게임에 맞춘 7가지 — 검색 요약으로 확인된 것은 「표지와 피드백(signs & feedback)」 · 「형태는 기능을 따른다」 둘이고, 나머지(명확성 · 일관성 · 최소 작업량 · 오류 예방/복구 · 유연성)는 그녀의 강연 자료에서 흔히 인용되는 목록이다 — 원문 대조 필요. 몰입성 = 동기 · 감정 · 몰입(flow). (https://www.routledge.com/The-Gamers-Brain-How-Neuroscience-and-UX-Can-Impact-Video-Game-Design/Hodent/p/book/9780367638184)
  → 실무 뜻: 사람의 작업 기억은 몇 덩어리뿐이다 — **한 창에 새 정보 덩어리는 3~4개**까지.
- **Pinelle · Wong · Stach (CHI 2008) 「Heuristic Evaluation for Games」**: 실제 리뷰 108개의 사용성 문제를 분류해 만든 게임 전용 휴리스틱 10개(https://course.ccs.neu.edu/is4300f15/ssl/pinelle-chi08.pdf). 논문을 직접 열지 못해 목록은 원문 대조가 필요하지만, 널리 인용되는 항목 중 UI에 직결되는 것: 행동에 일관되게 반응 · 시야를 가리지 않는다 · **게임 상태 정보를 보여 준다** · 반복되는 비(非)플레이 화면은 건너뛸 수 있게 · 조작이 직관적 · 화면 표현이 읽히게.
- **NN/g 「Modal & Nonmodal Dialogs」**: 모달은 뒤 화면을 막는 특별한 상태 — **중요하지 않은 일에 쓰면 문제**, 확인창 남발은 「읽지 않고 누르기」를 훈련시킨다(https://www.nngroup.com/articles/modal-nonmodal-dialog/). IBM Carbon: 모달은 상호작용 비용을 더한다. Fluent UI: 되돌릴 수 없거나 파괴적일 때만 「정말?」.
- **Xbox Accessibility Guidelines 101(글자 표시)**: 콘솔 1080p 기준 **본문 최소 26px**(약 화면 높이의 2.4%) — 우리 412 높이 환산 ≈ 10px, 휴대폰은 가까이 보므로 우리 본문 15px · 보조 12px는 기준 위(https://devdocs.xbox.com/gaming/accessibility/xbox-accessibility-guidelines/101). XAG 102: 대비 4.5:1.
- **Game UI Database**(Edd Coates, https://www.gameuidatabase.com): 1,300+ 게임 55,000+ 장, 「모달 · 오버레이」 · 화면 종류 · 재질(texture)로 거를 수 있다 — **새 창을 설계하기 전에 같은 종류의 화면 5장 이상을 먼저 본다** (이번 세션은 접속 불가였다; 사용자가 볼 수 있게 링크만).

### 1.11 엄지 영역 · 안전 영역 [2차]
- Steven Hoober 연구: 쉬운 영역 = 쥔 손 엄지가 닿는 아래쪽(https://uxmatters.com/mt/archives/2013/11/design-for-fingers-and-thumbs-instead-of-touch.php). 가로 모드는 대개 두 손으로 쥐어 엄지 영역의 무게가 덜하다는 견해(UXmag)와 「가까운 가장자리 쪽으로 옮겨 간다」는 견해가 함께 있다 — 가로 게임용 동료 심사 연구는 찾지 못했다. 우리가 쓰는 결론(추론): 두 엄지가 쉬는 **좌우 아래 가장자리**를 진행 · 건너뛰기 자리로, 위 가운데 · 위 모서리는 필수 단추에 쓰지 않는다. 최소 누름 ≈ 10mm 안팎.
- 게임 광고 160개 조사(AHFE 2024): 닫기 단추가 엄지가 닿지 않는 위 모서리에 놓이는 것이 불만의 원인.
- 노치 · 둥근 모서리: 가로 모드에서 좌우 안전 여백(`env(safe-area-inset-left/right)`)은 기기에 따라 **0~약 48 CSS px**. SPD도 창 가운데를 안전 영역 안에서 잡는다.

### 1.12 픽셀 UI 기법 · 오픈 키트 [1차 · 2차]
- 정수 배율 + 최근접(nearest) 확대 + 안티에일리어싱 끔 + PNG(JPEG 금지). 원본 9-slice는 16~32도트면 충분 — 키우는 일은 9-slice가 한다.
- **Kenney Pixel UI Pack**(CC0, 750타일, 16×16 격자 · 간격 2, https://www.kenney.nl/assets/pixel-ui-pack): 패널 · 단추 · 칸이 **같은 16도트 격자**, 단추는 보통 · 눌림 두 장이 한 쌍. 업계 기본형 — 상태 수와 격자 통일의 기준으로 쓴다.

## 3. 우리 게임의 규칙 — 915×412 기준 수치

### 3.0 단위
- **D** = 장치 층 1도트 = `--px` = **2 CSS px** (design-system 1장). 모든 틀 · 여백은 D의 정수배.
- 화면 = 915×412 CSS = **457×206 D**. (SPD 가로 가상 화면 400×180 도트와 같은 체급.)
- 안전 여백 `G` = max(16px, env(safe-area-inset-left/right)) 좌우, max(8px, env(safe-area-inset-top/bottom)) 위아래.
  → 노치 없는 기기 쓸 수 있는 칸: **883×396**, 노치 48px 기기: **819×396**.

### 3.0b 기기 행렬 (D-392 — PC · 모바일)
- 논리 화면(CSS px)은 **667×375 ~ 약 1000×560**: 작은 폰 667×375 · 기준 915×412(DPR 2.625) · PC 1080p는 일렉트론 ×2 확대로 960×540 · 1366×768 → 683×384 · 1440p → ×3 853×480.
- `--px` = round(2·DPR)/DPR (런타임) — 도트 = 기기 픽셀 정수. 모든 도트 단위 크기는 `calc(var(--px) * N)`.
- 점검은 세 곳: 667×375 DPR 2 · 915×412 DPR 2.625 · 960×540 DPR 2. L 창 = min(883, 100vw − 32), 높이 상한 = min(364, 100vh − 48).

### 3.1 창 크기 세 단계 (이 셋만 쓴다)
| 단계 | 폭 | 높이 상한 | 화면 대비 | 근거 | 쓰는 곳 |
|---|---|---|---|---|---|
| **S** | **352px (176D)** | 240px | 38% × 58% | SPD WndOptions 144도트 = 36% | 확인 · 경고 · 짧은 정보 |
| **M** | **592px (296D)** | 364px | 65% × 88% | SPD 정보창 최대 220도트 = 55%, 높이 94% | 하나 고르기 · 정보 상세 · 대화(그림 없음) |
| **L** | **min(883px, 100vw − 2G)** | 364px | ≈ 96% × 88% | — | 상점 · 대화(장면 그림 + 글) · 결과 요약 |
- 높이 상한 364 = 412 − 위아래 여백 8×2 − 명패가 위로 걸치는 16 − 바닥 그림자 · 여유 16.
- 폭은 위 셋 중 하나로 **고정**한다. 내용이 넘치면 ① 글을 줄이고 ② 한 단계 위 크기로 ③ 그래도 안 되면 화면을 둘로 나눈다(점진적 공개). **스크롤은 금지**(HIG). 예외: 덱 목록 같은 「모음」 화면은 L + 내부 스크롤 칸(`inset`) 하나.
- 정보창은 SPD처럼 **세로로 4줄을 넘기면 가로로 넓힌다**(S → M).
- 창은 안전 영역 안 **가운데**. 장면 그림이 있는 장소 화면은 그림 반대쪽(오른쪽)으로 붙이되 폭은 위 단계 그대로.

### 3.2 창 해부도 (모든 단계 공통)
```
          ┌──[ 황동 명패: 제목 ]──┐   ← 명패 높이 48px(24D), 패널 위 테에 절반(16px) 걸침, 가운데 정렬
┌─────────┴──────────────────────┴─────────┐ ← 패널 테 10px(5D) · 바닥 먹 그림자 4px(2D) 오른아래
│  안쪽 여백 12px(6D) · 명패 아래 첫 줄까지 28px          │
│  [머리 줄] 아이콘 24/48px + 부제 12px (선택)            │
│  [본문 블록] 15px 갈무리14, 줄높이 1.5 = 22.5px         │
│  ─ 묶음 사이 16px(8D), 묶음 안 8px(4D) ─              │
│  [선택 블록] 단추/카드/칸 — 간격 8px(4D)               │
│  [단추 줄] 높이 48px(24D) · 오른쪽 = 진행 · 왼쪽 = 취소  │
└──────────────────────────────────────────┘
```
- 패널 테 10px, 안쪽 여백 12px → **글이 놓이는 폭 = 창 폭 − 44px**: S 308px · M 548px · L 839px.
- 제목 명패: 24px 갈무리11 굵게(design-system 7.1), 명패 좌우 테 24px(12D) → 제목 글 **최대 12자**.
- 명패는 창마다 **하나**. 부제 · 꼬리표는 명패가 아니라 12px 황동 꼬리표.
- 닫기: 기본은 **단추 줄의 「닫는다/취소」** + 뒤 막(디더) 누르면 닫힘(SPD). 되돌릴 수 없는 선택을 기다리는 창(보상 · 사건 선택)은 뒤 막 눌러도 **안 닫힌다**(Blender HIG: 「바깥 누르기」를 유일한 안전장치로 두지 않는다). 모서리 X 단추는 쓰지 않는다 — 엄지에서 먼 위 모서리(1.11).
- 뒤 막: 지금의 2×2 먹 디더 막 그대로(D-262). 뒤 장면이 **보여야** 한다(SPD 50% · HIG 맥락 유지). 등장은 디더 3계단 200ms, 창은 m3in(예비 → 터짐 → 출렁임) — D-263.

### 3.3 단추 줄
- 높이 **48px(24D)** 고정 — Material 48dp · HIG 44pt. 단추 간격 **8px 이상**(SPD 2도트 ≈ 4.6px보다 넓게: 손가락).
- 개수: 가로 줄 **최대 2개**. 셋 이상의 선택은 단추 줄이 아니라 **선택 블록(세로로 쌓은 철 단추, 창 폭 전체)**(SPD WndOptions · HIG 「세로면 기본이 위」).
- 자리: **진행(황동) = 오른쪽 끝**, 취소 · 건너뛰기(철) = 왼쪽(HIG 끝쪽 규칙 + 가로 모드 오른손 엄지). 두 단추는 **같은 크기**, 재질로만 구별(HIG 「크기가 아니라 스타일로」).
- 이름: 동사 하나, **최대 6자**(voice ⑧). 결과 수치는 단추 안이 아니라 위 본문 · 꼬리표에(「정비 — 모두 HP +25%」 ✗ → 단추 「정비한다」 + 위 꼬리표 「분대 전원 HP +25%」).
- 진홍(되돌릴 수 없음)은 **의도하지 않은 파괴**일 때만, 그때는 철 「취소」를 반드시 같이(HIG).
- 단추 최소 폭 96px, 한 화면에 황동 단추 **1개**(눈에 띄는 단추 1~2개 — HIG).

### 3.4 글 위계 (허용 크기만 — D-213 · D-373)
| 층 | 크기 · 서체 | 쓰는 곳 | 한 줄 최대 |

| H1 화면 표제 | 36px 갈무리11 굵게 | 막 전환 · 결과 화면 큰 표지만 (창 안 금지) | 12자 |
| H2 창 제목 | 24px 갈무리11 굵게 | 황동 명패 안 | 12자 |

| 큰 수치 | 30px 갈무리14 | 보상 수치 · 가격 하나만 크게 | — |

### 3.5 DPR 2.625 함정 (확인 필요 · 제안)
- 2 CSS px × 2.625 = **5.25 기기 픽셀** — 도트가 5px · 6px로 섞여 9-slice 테 두께가 들쭉날쭉해진다(Godot 문서의 분수 배율 그림과 같은 현상). SPD는 배율을 **기기 픽셀 정수(6)**로 고른다.
- 제안: `--px`를 `round(2 × dpr) / dpr`로 JS에서 정한다(2.625 → 5/2.625 = **1.905 CSS px**, 기기 5px 고정). 모든 9-slice 테가 이 값의 정수배를 쓰면 테가 고르게 찍힌다. 바꾸기 전 실제 기기 확대 스크린샷으로 확인하고, 바꾸면 DECISIONS에 남긴다. (이 문서는 src를 고치지 않는다.)

### 3.6 받은 그림 넣기 (D-386)
- **비율을 절대 깨지 않는다.** 칸이 다르면 `object-fit: cover` / `background-size: cover` + 초점(`object-position`)으로 **잘라 쓴다**. `fill` · 한 축만 늘이기 · `100% 100%` 금지.
- 도트 그림은 **정수배**로만 키운다(원본 1도트 = 화면 정수 기기 픽셀이 이상, 최소 정수 CSS px). 정수배가 칸보다 크면 잘라 쓴다, 작으면 먹 테두리 액자에 넣는다 — 소수배로 맞추지 않는다.
- `image-rendering: pixelated`, PNG만. 그림 위에 글을 얹을 때는 그림의 **아래 1/4**(발주서의 「글이 얹히는 자리」)에만, 먹 띠(불투명) 위에.
- 안전 영역: 그림은 화면 끝까지 깔아도 되지만 **글 · 단추는 안전 영역 안**.

## 4. 팝업 분류 6종 — 레시피

> 먼저 「모달이 꼭 필요한가」(NN/g · HIG): 행동이 없는 정보 → **토스트 · 판 위 표시**, 되돌릴 수 있는 흔한 행동 → **확인 없이 하고 되돌리기**. 모달은 결정 · 되돌릴 수 없는 일 · 집중할 일에만.

### 4.1 확인 (Confirm) — S
- 쓰는 때: 되돌릴 수 없고 **드문** 행동만(런 포기 · 저장 지우기 · 덱에서 카드 영구 삭제). 턴 종료 · 이동 같은 흔한 행동엔 쓰지 않는다(ITB: 예고 + 되돌리기).
- 구성: 명패(동사구 제목 ≤ 12자) → 본문 **최대 2줄**(무엇이 사라지는지 결과 1문장, 합니다체) → 단추 줄 [취소(철, 왼쪽)] [동사(진홍 또는 황동, 오른쪽)].
- 세로 예산: 명패 걸침 28 + 본문 45 + 16 + 단추 48 + 테 · 여백 44 ≈ **181px** (≤ 240).
- 뒤 막 눌러 닫힘 = 취소.

### 4.2 하나 고르기 보상 (Pick-one) — M 또는 L
- StS 형: **선택지 3개(최대 4) + 건너뛰기 늘 보이게.**
- 구성: 명패(「전리품」 류 ≤ 12자) → 부제 12px 1줄(≤ 24자: 출처 · 남은 수) → **카드 줄**(실제 카드 얼굴 `cf`, 가로로, 카드끼리 16px) → 단추 줄 [건너뛴다(철, 왼쪽)] … [진행은 카드를 누르는 것 자체].
- 카드를 누르면 바로 확정하지 않고 **선택 테두리(청록) + 진행 단추 「고른다」 활성** → 두 번 탭 = 결정(실수 방지, 되돌릴 수 없으므로).
- 카드 글은 voice ⑥ + 카드 레이아웃(D-373) 그대로. 카드 아래에 **덱 영향 1줄**(「덱 폰 3」) 12px.
- 세로 예산(M, 카드 높이 ≤ 220): 28 + 18 + 8 + 220 + 16 + 48 + 22(아래 테 · 여백) = **360** (≤ 364). 카드가 220을 넘으면 L 창에 카드 축소가 아니라 **카드 수를 줄인다**.
- 정비 · 회복 같은 「덤 행동」은 별도 단추가 아니라 4번째 카드 칸 또는 다음 화면으로(단추 줄 2개 규칙).

### 4.3 정보 · 엿보기 (Info / Peek) — S → M
- 쓰는 때: 길게 누르기 · 「i」 · 용어. 행동 없음.
- 구성(SPD WndInfoItem 형): 머리 줄 = 아이콘 48px + 이름 24px(명패 대신 이 머리 줄을 써도 된다 — 작은 창) → 본문 **최대 4줄**(넘으면 M으로 넓힌다, 그래도 6줄 상한) → **단추 없음**, 아무 데나 누르면 닫힘.
- 용어는 voice ①: 최대 두 줄, 줄바꿈 자리 지정.
- 세로 예산(S): 48 + 8 + 90 + 44 = **190**.
- 판 위에서는 모달 대신 **비모달 툴팁 패널**(판을 가리지 않는 쪽 레일 위)로 — Cogmind · Pinelle 「메뉴를 뒤지지 않게」.

### 4.4 상점 (Shop) — L
- 구성: 명패(가게 이름) + 오른쪽 위 지갑(나사 수, 30px 숫자 + 아이콘) → **물건 격자 2줄 × 3~4칸**(물건 하나 = 카드 얼굴/아이콘 칸 + 아래 황동 가격 꼬리표 12px 굵게) → 오른쪽 또는 아래 **상세 칸 하나**(누른 물건 설명, 모달 안의 모달 금지 — HIG) → 단추 줄 [떠난다(철, 왼쪽)] [산다(황동, 오른쪽, 고른 물건이 있을 때만 활성)].
- 살 수 없는 물건: 가격 꼬리표 진홍 + 자물쇠 아이콘(색만으로 구분 금지).
- 장소 그림이 있으면 왼쪽 40%는 그림(cover로 자름), 창은 오른쪽 M 폭(592). 그림 쪽 창은 **불투명 9-slice 그대로**(반투명 금지).
- 세로 예산: 28 + 2×(카드 130 + 꼬리표 20) + 8 + 16 + 48 + 22 = **422 ✗** → 카드 축소본(높이 ≤ 110)을 쓰거나 1줄 × 4칸 + 상세 칸. **설계 전에 반드시 합을 계산**한다.

### 4.5 대화 · 사건 (Dialogue / Event) — L (장면 그림 있음) / M (없음)
- 구성(L): 왼쪽 **장면 그림 칸 4:3**, 높이 ≤ 300px(→ 폭 400), cover로 자름 + 먹 테 → 오른쪽 단(≤ 400px 폭):
  1. 명패: 사건 이름(≤ 12자)
  2. 서술(voice ⑤) **최대 2줄** — 문장마다 줄바꿈
  3. 대사 칸(`inset`): 화자 이름 12px 굵게 + 대사 **최대 2줄**(voice ④)
  4. 선택지 **최대 3개**, 세로로, 창 단 폭 전체 철 단추. 선택지 하나 = **이름 1줄(15px, ≤ 16자) + 결과 1줄(12px, ≤ 28자, 강조색 1개)**. 확률 · 대가의 세부는 선택지 오른쪽 「i」(SPD WndChooseAbility 20도트 정보 단추) 또는 고른 뒤 다음 화면에서.
- 세로 예산(오른쪽 단): 명패 걸침 28 + 서술 45 + 8 + 대사 칸 (12 테 + 18 + 45) 75 + 16 + 선택지 3×(15·1.4 + 12·1.4 + 단추 테 16 ≈ 54) 162 + 간격 16 + 아래 22 = **372 → 3개면 서술을 1줄로**(349). 이 합이 364를 넘으면 선택지 수가 아니라 **글을 줄인다**.
- 지금 「떠돌이 땜장이」 화면의 실패(2장)를 이 레시피로 고친다.

### 4.6 토스트 · 상태만 (Toast / State-only) — 모달 아님
- 쓰는 때: 행동이 필요 없는 알림(획득 · 저장 · 규칙 발동). HIG 「정보만 주는 경고창 금지」의 대체.
- 구성: 철판 패널 높이 **40~48px**, 글 15px **1줄 ≤ 20자**(시스템 투) 또는 독백 1줄. 아이콘 24px 하나 앞에.
- 자리: **판 위쪽 가장자리(레일 사이)** — 누를 필요가 없으니 엄지에서 먼 위쪽이 맞다. 판의 기물 · 과녁을 가리지 않는다. 동시에 **최대 1개**, 다음 것은 줄 세운다.
- 시간: 1.2초 + 글자당 70ms(design-system 7.1), 누르면 넘어감. 등장 · 퇴장은 디더 계단.
- 결과 알림(사건 결과)은 토스트가 아니라 **실제 카드 · 기물에 FX + 대사**(D-260).

## 6. 스크린샷 자체 점검표 (사용자에게 보이기 전에 — 하나라도 ✗면 고친다)
915×412, DPR 2.625에서 찍은 스크린샷을 **원본 크기로 열어** 본다.
1. **잘림**: 창 · 글 · 단추가 화면(안전 영역) 안에 다 있다. 스크롤바 · 말줄임 · 잘린 글자 없음. (`node tools/artguide/ui-audit.cjs <폴더>`의 `TXT` 줄 0개)
2. **크기 단계**: 창 폭이 352 / 592 / 883 중 하나다(브라우저 개발자 도구로 잰다).
3. **세로 예산**: 창 높이 ≤ 364, 명패가 위 테에 걸쳐 있다.
4. **5초 테스트**: 스크린샷을 5초 보고 「이 창이 무엇을 묻나 / 무엇을 누르면 어떻게 되나」를 한 문장으로 말할 수 있다.
5. **덩어리 수**: 새 정보 덩어리 ≤ 4(제목 · 본문 · 선택 · 단추). 글 줄 수가 4장의 예산 안.
6. **글 위계**: 크기 3단 이하, 모두 허용 크기, 한 줄에 색 1개 + 강조 1개.
7. **단추**: 높이 ≥ 48, 간격 ≥ 8, 진행 오른쪽 · 취소 왼쪽, 같은 크기, 동사 ≤ 6자, 황동 1개.
8. **도트**: 테 두께가 사방 같다(확대해 보고 5px · 6px 섞임 확인), 흐린 가장자리 없음, 반투명 패널 없음.
9. **그림**: 받은 그림의 비율이 원본과 같다(원과 사각이 찌그러지지 않음), 소수배 확대 없음.
10. **맥락**: 뒤 막 너머 장면이 보인다(무엇 위에 떠 있는지 안다).
11. **엄지**: 진행 · 건너뛰기가 아래 절반에 있다. 위 모서리에 필수 단추 없음.
12. **말투**: 문장마다 voice 갈래 하나, 단추는 동사, 느낌표 없음(치명적 순간 제외).
13. **움직임**: 등장 디더 계단 · m3in, 투명도 보간 · 선형 슬라이드 없음 — 녹화 또는 3프레임 연속 캡처로 확인.
판정은 ux-review처럼 APPROVED / NEEDS REVISION — 확인 못 한 항목은 NOT ASSESSED.
